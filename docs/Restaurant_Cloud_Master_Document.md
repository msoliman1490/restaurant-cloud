# Restaurant Cloud — الوثيقة المرجعية الرئيسية للمشروع

**الإصدار:** 1.0  
**التاريخ:** 7 نوفمبر 2026  
**الحالة:** وثيقة دراسة ومواصفات موحدة — ليست تصريحًا ببدء التنفيذ  
**السوق:** المملكة العربية السعودية  
**المنتج:** منصة SaaS مستقلة لإدارة المطاعم والكافيهات والتموينات

> **تعليمات إلزامية لـ Antigravity وLovable وأي أداة ذكاء اصطناعي:** هذه الوثيقة للدراسة والتحليل فقط. يُمنع إنشاء أو تعديل أو حذف أي كود أو ملفات أو جداول أو قواعد بيانات أو migrations أو إعدادات أو خدمات. يُمنع تشغيل أوامر بناء أو نشر أو ترحيل. المطلوب هو قراءة الوثيقة وإعداد ملاحظات التعارض والنواقص والمخاطر فقط. لا يبدأ التنفيذ إلا بأمر صريح مستقل من مالك المشروع.

---

## 1. الملخص التنفيذي والرؤية

Restaurant Cloud منصة تشغيل وإدارة مالية ومخزنية متكاملة للمطاعم والكافيهات والتموينات، تخدم المنشآت الصغيرة والمتوسطة والمجموعات متعددة الشركات والفروع. المنتج SaaS مستقل قابل للتشغيل بنموذج Shared SaaS أو Dedicated Deployment.

المنصة ليست POS فقط؛ بل تربط الطلبات والبيع والمدفوعات والمخزون والوصفات والإنتاج والمشتريات والمحاسبة والفوترة الإلكترونية والتوصيل والتكاملات والتقارير في دورة عمل واحدة.

**القيمة الأساسية:** تجربة بيع سريعة، مخزون وتكلفة موثوقان، محاسبة متكاملة، تعدد شركات وفروع، تشغيل Offline مضبوط، وتكاملات قابلة للصيانة.

هذه الوثيقة مواصفات تصميمية. لم تُجرَ بالضرورة مقابلات السوق أو اختبارات المنافسين أو POCs أو اختبارات الأجهزة أو اعتماد ZATCA. يجب تنفيذها والتحقق من المتطلبات الرسمية الحالية قبل الإطلاق.

## 2. أهداف المنتج ومؤشرات النجاح

### أهداف الأعمال
- تقليل زمن الطلب والدفع وإقفال الوردية.
- تقليل فروق المخزون والهالك غير المفسر.
- إظهار هامش الربح بعد تكلفة الوصفات والمرتجعات والخصومات.
- منع الإدخال المكرر بين POS والمخزون والمحاسبة.
- إدارة الفروع والمجموعات من منصة واحدة مع فصل قانوني صحيح.
- تقديم اشتراكات وإضافات وخدمات قابلة للتوسع.

### مؤشرات الأداء
تحدد المستهدفات النهائية بعد Pilot وقياس الاستخدام الفعلي:
- زمن استجابة POS وواجهات API (P50/P95).
- نسبة نجاح مزامنة Offline.
- عدد العمليات المالية/المخزنية المفقودة أو المكررة؛ الهدف صفر.
- دقة تكلفة الصنف والوصفة.
- فروق الجرد والهالك.
- زمن إقفال الوردية ومطابقة وسائل الدفع.
- نسبة قبول/إبلاغ الفواتير لدى ZATCA.
- التوافر ووقت الاستعادة وتكلفة تشغيل العميل.

## 3. السوق والعملاء ونموذج الإيرادات

### السوق والشرائح
السعودية هي سوق الإطلاق الأول. الشرائح:
1. منشأة صغيرة بفرع واحد أو عدد محدود من الأجهزة.
2. مطعم أو كافيه نامٍ متعدد الفروع.
3. مجموعة تشغيل بعدة علامات أو شركات قانونية.
4. تموينات ومتاجر أغذية تعتمد على الباركود والوزن والصلاحية.
5. عملاء كبار يحتاجون عزلًا أعلى أو Dedicated Deployment.

### نموذج الإيرادات
نموذج Hybrid:
- اشتراك أساسي.
- حدود استخدام حسب الخطة (فروع، أجهزة، مستخدمون، وحدات).
- إضافات مدفوعة مثل WhatsApp وSMS وAPI والتقارير المتقدمة.
- خدمات تهيئة وتدريب وترحيل بيانات ودعم مميز وتكاملات مخصصة وDedicated.

لا توجد أسعار أو حدود باقات معتمدة. Start / Business / Pro / Enterprise أسماء تقسيم مبدئية فقط.

### تحقق السوق
تُجرى مقابلات مع منشآت متنوعة، واختبارات عملية للمنافسين مثل Foodics وMarn وOdoo وQoyod وRewaa، مع مقارنة POS والمخزون والوصفات والمحاسبة والفوترة الإلكترونية وOffline والتكلفة. لا تعتبر هذه الوثيقة نتائج تلك الاختبارات. Pilot مقترح من 8–12 منشأة متنوعة، ولم يُنفذ بعد.

**قاعدة ضبط النطاق:** لا تُعتبر الشاشة مكتملة لمجرد ظهورها. كل ميزة تحتاج قواعد أعمال وصلاحيات وحالات وأثر مالي/مخزني واختبارات قبول.

## 5. الهيكل التنظيمي وتعدد الشركات

### الكيانات
- **Tenant:** عميل المنصة وحدود العزل والاشتراك.
- **Group:** مجموعة تشغيلية.
- **Legal Entity:** شركة قانونية مستقلة لها رقم ضريبي ودفاتر وترقيم وإعدادات فوترة.
- **Branch:** فرع تشغيلي.
- **Warehouse:** مخزن مادي أو موقع تخزين.
- **POS Device:** جهاز بيع مرتبط بفرع ونطاق صلاحيات.
- **User / Membership:** هوية المستخدم وعضويته ونطاق وصوله.

لا تخلط Tenant مع Legal Entity. يمكن أن يحتوي Tenant مجموعة شركات قانونية متعددة. لكل شركة دفاترها وضريبتها وترقيمها، مع تقارير Consolidated للمجموعة.

### ملكية المخزون
يمكن أن يخدم المخزن المادي أكثر من شركة، لكن الملكية والتكلفة والحركات منفصلة حسب الشركة المالكة. الكتالوج مركزي، والأسعار وإعدادات الأصناف والوصفات قابلة للتخصيص حسب الفرع.

### الصلاحيات
نطاقات الصلاحيات: Tenant، Group، Legal Entity، Branch، Warehouse، POS Device، Module/Action. أدوار نموذجية: Platform Admin، Tenant Owner، Group Manager، Company Manager، Branch Manager، Accountant، Inventory Controller، Procurement، Cashier، Kitchen، Delivery، Auditor.

الخادم يعيد التحقق من نطاق الوصول لكل طلب. RLS طبقة دفاع إضافية وليس بديلًا عن تفويض الخادم. يجب دعم MFA للأدوار الحساسة، أقل صلاحية، وفصل الواجبات SoD.

## 6. تجربة الاستخدام والواجهات

### مبادئ UX
- العربية RTL والإنجليزية LTR.
- POS للمس والكيبورد ولا يعتمد على Hover.
- خطوات قليلة للكاشير مع تحقق كافٍ.
- إظهار حالات الاتصال والمزامنة بوضوح.
- تعطيل الزر أثناء الإرسال لتحسين UX، لكن ضمان عدم التكرار يأتي من الخادم وقاعدة البيانات.
- رسائل خطأ مفهومة ومرجع تتبع.

### خريطة الشاشات
- إدارة المنصة: العملاء، الاشتراكات، الاستخدام، الدعم، المراقبة.
- الإعداد: الشركات، الفروع، المخازن، المستخدمون، الضرائب، POS، الدفع.
- التشغيل: POS، الطلبات، الطاولات، KDS، التوصيل، الورديات.
- المنتجات: الأصناف، التصنيفات، الوحدات، الباركود، الأسعار، الوصفات.
- المخزون: الأرصدة، الحركات، التحويلات، الجرد، الهالك، الصلاحية.
- المشتريات: الموردون، الطلبات، أوامر الشراء، الاستلام، فواتير الموردين.
- المالية: الحسابات، القيود، الخزائن، البنوك، التسويات، الأصول، الضرائب، القوائم.
- الإدارة: لوحات حسب الدور، تقارير، Drill-down، رادار المشكلات.

### POS
يدعم Dine-in وTakeaway وDelivery، الطاولات والمناطق، الإضافات والمعدلات، تعليق الطلب واستئنافه، تقسيم/دمج الفاتورة حسب الصلاحية، دفعًا مختلطًا، خصومات بحدود، مرتجعات وإلغاءات معتمدة، تذاكر مطبخ ومشروبات، فتح وإغلاق الوردية، واختصارات قابلة للتخصيص.

### الطباعة
Print Template Engine مستقل لقوالب الفاتورة المبسطة والكاملة، المطبخ والمشروبات، إيصال الدفع، المرتجع، إقفال الوردية والتقارير والسندات. يدعم 58mm و80mm وA4 وA5 ومقاسًا مخصصًا، RTL/LTR، معاينة وإصدارات. إعادة الطباعة لا تنشئ أثرًا جديدًا، والقالب لا يغير البيانات الضريبية أو QR أو XML.

## 7. الوحدات الوظيفية وقواعد الأعمال

### الكتالوج والتسعير
كتالوج مركزي، تصنيفات وعلامات ووحدات وتحويلات وباركود. أنواع الأصناف: مخزني، خدمة، خام، تعبئة، جاهز، نصف مصنع، مستلزم، غير مخزني. أسعار حسب الفرع أو القناة أو قائمة الأسعار. التغييرات المؤثرة ذات إصدارات وتواريخ سريان.

### اختلاف الأنشطة
محرك مشترك وقوالب:
- المطاعم: طاولات ومناطق وطلبات وKDS ومحطات تحضير.
- الكافيهات: أحجام، ساخن/بارد، حليب، سكر، شوتات، نكهات ومحطات مشروبات.
- التموينات: باركود، وزن، عروض، أسعار جملة، صلاحية ودفعات.
يمكن للمجموعة تشغيل أنشطة مختلفة. لا تُبنَ ثلاثة تطبيقات مستقلة ولا تفرض خصائص نشاط على نشاط آخر.

### الطلبات والمبيعات
حالات مرجعية: Draft → Confirmed → In Preparation → Ready → Served/Dispatched → Completed، مع حالات إلغاء ومرتجع مستقلة. كل طلب UUID. الفاتورة تسجل تشغيليًا وضريبيًا. الإلغاء والمرتجع مستند عكسي مرتبط بالأصل، وليس حذفًا للأثر. الخصومات حسب حدود وصلاحيات.

### الوصفات والإنتاج
وصفات بإصدارات وتاريخ سريان، مكونات ووحدات، Yield وفاقد، Sub-recipes وModifiers وتخصيصات الفروع. أوامر إنتاج واستهلاك وإخراج ومطبخ مركزي. دعم تكلفة المواد، مع تصميم يسمح بتحميل العمالة والتكاليف غير المباشرة لاحقًا. يجب اعتماد سياسة التحميل قبل تثبيت تقارير الربحية النهائية.

### المخزون
مستويات Group / Legal Entity / Branch / Warehouse / Location / POS allocation. كل حركة تحمل المالك والموقع والسبب والمصدر. منع المخزون السالب افتراضيًا. الجرد والهالك والتالف والانتهاء أسباب مستقلة. FEFO للصرف التشغيلي للصلاحية، وليس طريقة تقييم تكلفة. التحويل بين الشركات يعالج حسب طبيعته القانونية والضريبية. لا تعدل الحركة المرحلة؛ التصحيح بحركة عكسية أو تسوية.

### تقييم التكلفة
دعم FIFO وWeighted Average. التوصية المبدئية أن تكون طريقة التقييم لكل شركة في الإصدار الأول، مع إمكانية توسعة النطاق مستقبلًا. لا تغيير بأثر رجعي دون معالجة محاسبية معتمدة. استخدم Decimal/Numeric ولا تستخدم Floating Point للأموال.

### المشتريات
موردون وشروط دفع، طلب شراء وموافقة، أمر شراء، استلام جزئي/كامل، مطابقة أمر الشراء والاستلام والفاتورة، GRNI، Landed Costs، مرتجع مرتبط بالأصل. سند السداد لا يسجل مصروفًا جديدًا إذا كان يسدد التزامًا سابقًا.

### المحاسبة
دفاتر مستقلة لكل Legal Entity، دليل حسابات قابل للتهيئة، قيد مزدوج، Journals، حالات Draft/Validated/Posted/Reversed، مراكز تكلفة، AR/AP، خزائن وبنوك، ضريبة، أصول وإهلاك، تسويات بنكية، فترات وإقفال، قوائم مالية، Intercompany وتقارير موحدة للمجموعة. لا تعديل أو حذف للقيد المرحّل؛ التصحيح بقيد عكسي أو تسوية.

### قيود POS وإقفال الورديات
القرار المبدئي المعتمد: لا قيد يومية لكل فاتورة POS. كل فاتورة مستقلة تشغيليًا وضريبيًا، ويُنشئ إقفال الوردية قيدًا مجمعًا مرتبطًا بالفواتير والحركات. يتضمن القيد المبيعات والخصومات والمرتجعات والضريبة والنقدية وتسوية البطاقات وتكلفة البضاعة والمخزون والفروق حسب الحالة. الافتراضي قيد إقفال لكل وردية مع منع التكرار. المرتجعات اللاحقة تعالج بدورة مستقلة مرتبطة بالأصل. إقفال الوردية ليس إقفال الفترة.

### الخزائن والمصروفات
خزائن متعددة للشركة والفرع، أمين صندوق، رصيد افتتاحي، تغذية، تحويل، جرد، فروق وإقفال يومي. مصروف نقدي أو آجل أو متكرر وتصنيفات تشغيلية. التحويل بين صناديق وبنوك وشركات بقيد صحيح. فصل المصروف عن سداد الالتزام.

### المدفوعات
نقدي وبطاقات ووسائل رقمية معتمدة ودفع مختلط. حسابات تسوية لكل مزود عند الحاجة. رسوم المزود والإيداعات البنكية تسجل عند تحققها. اختيار الكاشير لطريقة الدفع ليس تأكيدًا. Offline للبطاقات فقط إذا دعم الجهاز/المزود ذلك فعليًا وأكد العملية.

### الموارد البشرية P0
ملفات الموظفين والحضور والانصراف والإضافي والغياب والتأخير والسلف والعهد. الرواتب الكاملة مؤجلة. السلفة: طلب ثم موافقة ثم صرف ثم رصيد مستحق ثم سداد/أقساط ثم إقفال. العهد النقدية والعينية لها دورة تسليم وتسوية واسترداد. لا تدّع امتثالًا نظاميًا قبل مراجعة المتطلبات والتكاملات السعودية.

### التوصيل والعملاء والولاء
قنوات الطلب والسائقون والمناطق ورسوم التوصيل وحالات التسليم وربط الطلب بالعميل والفرع والقناة. CRM أساسي، موافقات الاتصالات والتسويق، ولاء ونقاط وفق سياسة. منصات التوصيل عبر Connectors مستقلة.

### التقارير والذكاء
تقارير مبيعات وربحية ومخزون وهالك ووصفات وإنتاج وورديات ومدفوعات وقوائم مالية. Drill-down إلى المستند والحركة والقيد. تصدير وجدولة حسب الصلاحيات. Financial Intelligence يقدم تنبيهات وتوقعات ولا يغير القيود أو المخزون تلقائيًا دون موافقة.

## 8. الترقيم ودورة المستند

لكل شركة قانونية إعدادات ترقيم مستقلة، ولكل نوع مستند/قيد تسلسل مستقل، مع إمكانية نطاق فرع. إعدادات التسلسل تشمل البادئة والسنة ورقم البداية وعدد الخانات والتسلسل المستمر أو السنوي وتاريخ بدء الإعداد.

- التخصيص ذري من قاعدة البيانات.
- ممنوع `MAX()+1` في الواجهة أو منطق غير محمي.
- لا يعاد استخدام رقم مستند مرحّل أو مسجل رسميًا.
- UUID داخلي ثابت مستقل عن الرقم الظاهر.
- تغيير الإعداد لا يغير المستندات التاريخية.
- رقم المستند المصدر يختلف عن رقم القيد ودفعة الترحيل.
- تسلسل EGS/ZATCA منفصل عن الترقيم الداخلي.

لكل نوع مستند دورة خاصة: إنشاء، تحقق، اعتماد، ترحيل، إلغاء/عكس، ربط بالمصدر، معالجة فشل ومصالحة.

## 9. ZATCA والفوترة الإلكترونية

### التصميم
وحدة E-Invoicing Compliance Engine مستقلة عن POS وعن إرسال الفاتورة. تفصل بين مستند البيع، EGS، بناء XML والتحقق، التوقيع والهاش، QR، Clearance/Reporting، والأرشفة والردود.

### EGS والشهادات
يدعم النظام عدة وحدات EGS. لا تفترض أن كل شاشة POS هي EGS مستقل؛ قد تعمل عدة شاشات عبر EGS أو Branch Server حسب النموذج المعتمد. إذا اعتمد EGS مستقل لكل جهاز، فلكل وحدة شهادتها ومفاتيحها وتسلسلها وسلسلة الهاش. مفاتيح التوقيع لا توضع في React أو LocalStorage أو JavaScript؛ تحفظ في Secret Manager أو مخزن مفاتيح آمن.

### البيانات والأنواع
تصميم يدعم UUID وICV وPIH وXML وHash وDigital Signature وQR وبيانات البائع والمشتري والضريبة والإشعارات الدائنة والمدينة وربطها بالأصل، وفق أحدث مواصفات الهيئة.

المبسطة تخضع للإبلاغ ضمن المهلة النظامية، والكاملة لمتطلبات Clearance قبل تسليمها كفاتورة مكتملة وفق الحالة النظامية. Offline لا يعفي من ZATCA. الحالات: Draft، Locally Generated، Signed، Pending Reporting، Pending Clearance، Cleared، Reported، Rejected، Reconciliation Required. الطباعة لا تعني قبول الهيئة. Sandbox لا يعني اعتمادًا رسميًا. يجب مراجعة أحدث وثائق الهيئة قبل التنفيذ والإطلاق.

## 10. Offline POS والمزامنة

### النموذج
Hybrid: Cloud + Branch Server على شبكة الفرع + Local Store على جهاز POS. يدعم PWA وElectron كمرشحين، والاختيار النهائي بعد POC للطباعة والأجهزة والتحديثات والعمل المحلي والأمان.

### المخزون عند الانقطاع
المخزون Shared Local في التشغيل الطبيعي. عند تعطل Branch Server لا يمكن ضمان رصيد موحد بين أجهزة غير متصلة. لا يسمح ببيع الرصيد نفسه من عدة أجهزة مستقلة. التوصية استمرار محدود بحصص مخزون حصرية مسبقة لكل جهاز، ومنع البيع دون كمية مؤكدة. القرار النهائي ما زال مفتوحًا بين إيقاف البيع أو الاستمرار المحدود أو الاستمرار الكامل مع قبول التعارضات؛ التوصية الخيار الثاني. يمنع المخزون السالب.

### الدفع
النقدي وفق سياسة الفرع. البطاقة لا تعتبر مدفوعة بمجرد اختيارها. يسمح Offline فقط إذا أكد الجهاز/المزود تنفيذ العملية. الحالات غير المؤكدة تبقى Pending/Unknown ولا تسجل كتحصيل نهائي.

### المزامنة
كل عملية لها UUID وIdempotency Key وDevice ID وBranch ID وتسلسل محلي ووقت إنشاء واستلام وPayload Hash وحالة مزامنة ومرجع المصدر. يستخدم Outbox/Inbox وUnique Constraints وReconciliation. لا ندّعي Exactly Once عبر الأنظمة الخارجية؛ نستخدم تسليمًا قابلًا لإعادة المحاولة مع Deduplication وآثار ذرية.

لا تستخدم Last Write Wins لحل تعارضات مالية أو مخزنية. المستند المعتمد لا يدمج تلقائيًا. حالات التعارض تدخل Reconciliation Queue مع سجل أصل وتصحيح.

### اختبارات Offline
قطع الإنترنت، تعطل Branch Server، انقطاع LAN والكهرباء، إعادة التشغيل، امتلاء المساحة، تكرار Outbox، اختلاف الساعة، بيع متزامن، تعطل الطابعة، الاستعادة، آلاف العمليات، رفض ZATCA، والتحقق من عدم الفقد أو التكرار.

## 11. Integration Hub

وحدة مستقلة لكل التكاملات. الأولوية لواتساب الرسمي عبر WhatsApp Business Platform / Cloud API أو BSP معتمد؛ لا يعتمد الإنتاج على WhatsApp Web غير الرسمي.

### WhatsApp Inbox
إرسال واستقبال، قوالب، حالات إرسال وتسليم، محادثات، توزيع على الموظفين، ملاحظات داخلية، بحث، ربط العميل والطلب والفرع، وإشعارات تأكيد الطلب والتجهيز والجاهزية والتوصيل والفاتورة والدفع. تطبق موافقات العميل وسياسات القوالب والتسويق.

### Connectors
WhatsApp، SMS، Email، Payment Gateways/Terminals، Delivery Platforms، E-commerce، Accounting، Maps، Storage، HR، External APIs. كل Connector مستقل بعقد موحد.

### Webhook Engine
Signature Verification، حفظ الحد الأدنى من Raw Event، External Event ID، Deduplication، Queue، Validation، Audit، Retry مع Backoff، Dead Letter، Reconciliation، Rate Limiting ومراقبة التأخير والفشل.

### حالات التكامل
Queued، Processing، Succeeded، Failed Retryable، Failed Permanent، Unknown، Reconciliation Required، Dead Letter. إذا انقطع الاتصال بعد طلب مزود خارجي ولم نعرف هل نفذه، لا نعيد الطلب عشوائيًا؛ نتحقق أو نستخدم idempotency لدى المزود أو نصعّد للمصالحة.

### API Platform
REST/OpenAPI، Versioning، OAuth 2.0 أو مصادقة مناسبة، API Keys للخدمات، Webhooks، Rate Limits، Sandbox، Developer Portal لاحقًا، Scopes دقيقة وUsage Metering.

### الأمان والقياس
الأسرار على الخادم، TLS، منع SSRF، التحقق من توقيع Webhook، أقل قدر من PII، عدم تسجيل الأسرار، وقياس WhatsApp/SMS/API/Webhook/Storage ورسوم المزود.

## 12. SaaS والاشتراكات والنشر

Shared SaaS هو النمط الافتراضي مع عزل منطقي قوي. Dedicated Deployment للعملاء ذوي الحاجة. نفس التطبيق ونفس منطق الأعمال قدر الإمكان، ولا تنشأ نسخ Fork مختلفة لكل عميل. العزل Hybrid: قاعدة مشتركة للعملاء العاديين وقواعد/بيئات منفصلة للعملاء الكبار.

Subscription Engine يدير الخطط ودورة الفوترة والتجربة والتعليق والإلغاء والتجديد وEntitlements والحدود والاستهلاك والإضافات وفواتير المنصة. يجب فصل اشتراك المنصة عن فواتير مبيعات المطعم.

نقل Shared إلى Dedicated يحافظ على UUID والمراجع، ويشمل تصديرًا مشفرًا، تحققًا، مزامنة أثناء النقل، نقطة تحويل تمنع الكتابة المزدوجة، مطابقة مالية ومخزنية، اختبارًا بعد النقل وخطة Rollback.

### المبدأ
Modular Monolith كبداية، وليس ملفًا أو صفحة ضخمة ولا Microservices مبكرًا. كل وحدة لها حدود ومسؤوليات وعقود واختبارات، ويمكن فصلها مستقبلًا عند وجود مبرر تشغيلي.

### الطبقات

- Application: Use Cases وتنسيق العمليات.
- Domain: قواعد الأعمال والكيانات والسياسات.

- Tests: Unit/Integration/Acceptance.

لا تضع قواعد المحاسبة أو المخزون في React. لا استعلامات DB عشوائية من الواجهات. لا تكرر قواعد الأعمال.

### الوحدات
Identity & Access؛ Tenant & Organization؛ Subscription؛ Branch & Device؛ Catalog & Pricing؛ POS & Orders؛ Kitchen/KDS؛ Inventory & Costing؛ Recipes & Production؛ Procurement؛ Accounting & Finance؛ Payments & Reconciliation؛ E-Invoicing؛ Delivery؛ CRM & Loyalty؛ Printing؛ HR Core؛ Integration Hub؛ Reporting؛ Audit؛ Platform Admin؛ Offline Sync & Branch Runtime.

### تقنيات مرشحة تحتاج POC

## 15. الأمان والخصوصية

- MFA للأدوار الحساسة، RBAC + Scopes، أقل صلاحية، تحقق خادمي في كل عملية.
- TLS وتشفير البيانات الحساسة وإدارة أسرار مركزية.
- لا أسرار في Frontend أو المستودع أو Logs.
- جلسات آمنة وإبطال جلسات وحماية Brute Force.
- Input Validation وOutput Encoding وCSP/CORS/CSRF حسب التطبيق.
- Rate Limiting وحماية SQL Injection وXSS وSSRF وMass Assignment.
- توقيع Webhooks وحماية رفع الملفات.
- فصل بيانات العملاء واختبارات عزل آلية.
- Audit Log للفاعل والوقت والجهاز والنطاق والعملية والقيم والتبرير وCorrelation ID ومصدر العملية.
- لا تسجل كلمات مرور أو مفاتيح توقيع أو بيانات بطاقات حساسة.
- دعم المنصة لبيانات العميل يكون بتفويض محدود المدة والنطاق ومسجل.

## 16. الأداء والموثوقية والتعافي

- Server-first للعمليات الحساسة.
- Server-side pagination/filtering.
- Indexes حسب الاستخدام الفعلي.
- تجنب N+1 وConnection Pooling.
- Cache للبيانات المرجعية فقط؛ لا يكون مصدر حقيقة للأرصدة أو القيود.
- Background Jobs للعمليات الطويلة.
- فصل التقارير الثقيلة عند الحاجة.
- Health Checks وRetries مع Backoff/Jitter وCircuit Breaker وDead Letter وGraceful Degradation.
- Logs/Metrics/Traces وCorrelation IDs.

أهداف أولية للاختبار وليست ضمانات: API عادي P95 قرابة 300ms، قراءات تشغيلية P95 قرابة 500ms، إنشاء مستند P95 قرابة 700ms باستثناء الطرف الثالث. تُراجع بعد القياس.

يجب تحديد RPO/RTO تجاريًا وتقنيًا قبل الإنتاج. المطلوب نسخ احتياطي مشفر وخارج نطاق الفشل، اختبار استعادة دوري، DR Runbook، والتحقق من اتساق قاعدة البيانات والملفات وأرشيف الفوترة. لا توجد قيم RPO/RTO معتمدة حاليًا.

| 2 | العملات | SAR فقط / Multi-currency مع عملة أساسية لكل شركة | تصميم Multi-currency مع إمكانية تقييد الواجهة أولًا |
| 3 | تكلفة الإنتاج | مواد فقط / مواد وعمالة وغير مباشرة / دعم الطريقتين | دعم الطريقتين والبدء بالمواد |
| 4 | توقف Branch Server | إيقاف / حصص محدودة لكل جهاز / استمرار كامل مع التعارض | الحصص المحدودة |
| 5 | ربط EGS | لكل POS / لكل فرع / مختلط | يحسم عبر ZATCA وPOC |
| 6 | RPO/RTO | مستويات حسب الباقة | يحدد قبل الإنتاج |
| 7 | التسعير | فروع/أجهزة/مستخدمون/استخدام/مزيج | Hybrid شفاف |
| 8 | الاحتفاظ | حسب نوع السجل والالتزام | سياسة احتفاظ مفصلة |
| 9 | عملة المجموعة | موحدة أم لكل شركة | عملة أساسية لكل شركة وتقارير تحويل |
| 10 | الموافقات | حدود ثابتة أم قابلة للتهيئة | محرك مركزي قابل للتهيئة |

Multi-currency يتطلب تخزين العملة الأصلية وسعر الصرف ومصدره وتاريخه والمبلغ الوظيفي. لا تغيّر طريقة تقييم المخزون بأثر رجعي. قرار Offline يوازن الاستمرارية وسلامة المخزون. قرار EGS يخضع للمتطلبات الرسمية وتصميم التشغيل الفعلي.

## 23. المخاطر والتخفيف

| الخطر | التخفيف |
|---|---|
| تضخم النطاق | فصل P0/P1/P2 وبوابات اعتماد |
| تعقيد Offline | POC مبكر، Outbox/Inbox، حصص، اختبارات انقطاع |
| خطأ مالي/مخزني | قواعد خادمية، معاملات، قيود، اختبارات مطابقة |
| تسرب Tenant | RLS + تفويض خادمي + اختبارات عزل |
| رفض ZATCA | مراجعة أحدث المواصفات وEGS واختبارات |
| تعطل مزود خارجي | Circuit Breaker، Unknown، Reconciliation |
| بطء النظام | Pagination، Indexes، قياس وفصل التقارير |
| اختلاف الفروع | إعدادات قابلة للتهيئة دون Fork |
| ترحيل خاطئ | Mapping ومطابقة وتجربة وRollback |
| تكلفة Dedicated | تسعير تكلفة التشغيل ومستويات الخدمة |
| الاعتماد على AI دون تحقق | مراجعة بشرية واختبارات وأدلة تشغيل |

## 24. بوابات الجاهزية قبل التنفيذ

لا يبدأ التنفيذ قبل:
1. اعتماد نطاق P0.
2. حسم القرارات المفتوحة المؤثرة على البيانات.
3. مراجعة SRS وقواعد الأعمال.
4. مراجعة ERD والقيود والفهارس.
5. مراجعة API Contracts وDomain Events.
6. مراجعة حدود الوحدات والمعمارية.
7. POC لـ Offline والطباعة والأجهزة.
8. POC لـ EGS/ZATCA وفق المتطلبات السارية.
9. خطة أمن وعزل.
10. خطة Backup/DR وتحديد RPO/RTO.
11. خطة اختبارات ومعايير قبول.
12. خطة Pilot وترحيل.
13. CI/CD ومراقبة.
14. تقدير تكلفة تشغيل Tenant/Branch/Device.
15. أمر صريح من مالك المشروع ببدء التنفيذ ونطاقه.

## 25. تعليمات تسليم الوثيقة إلى Antigravity أو Lovable

عند إرفاق الملف:
- اقرأ الوثيقة كاملة.
- لا تكتب كودًا ولا تنشئ/تعدل/تحذف ملفات.
- لا تنفذ SQL أو Migrations أو أوامر تشغيل أو نشر.
- لا تثبت Dependencies ولا تغير إعدادات أو قواعد بيانات.
- لا تفترض اعتماد القرارات المفتوحة.
- أخرج تقرير مراجعة فقط: فهم النطاق، التعارضات، النواقص، المخاطر، الأسئلة الجوهرية، POCs المطلوبة، والوحدات واعتمادياتها.
- لا تقترح اختصارًا يضر الذرية أو العزل أو سلامة القيود أو ZATCA.
- لا تعتبر نجاح الشاشة أو API دليلًا على صحة العملية.
- التنفيذ يحتاج أمرًا منفصلًا وصريحًا من مالك المشروع.

## 27. الخلاصة

يجب بناء Restaurant Cloud كنظام تشغيل ومحاسبة ومخزون متكامل، لا مجموعة شاشات. سلامة البيانات والأثر المالي والضريبي أهم من إطلاق وظائف غير مكتملة. العمليات الحساسة Server-first ومحميّة بمعاملات ذرية وقيود DB ومفاتيح منع تكرار وترقيم ذري وسجلات تدقيق ومصالحة.

الاختيار المعماري الأساسي Modular Monolith بحدود واضحة. يجب إثبات Offline والطباعة والأجهزة وEGS/ZATCA عبر POCs واختبارات فعلية قبل الإنتاج. هذه الوثيقة مرجع موحد للمواصفات في إصدارها الحالي، وأي تغيير لاحق يسجل بإصدار وسبب وأثر على الوظائف والبيانات والاختبارات والتكلفة.

**هذه الوثيقة لا تعني أن الاختبارات قد نُفذت أو أن المنتج معتمد ضريبيًا أو جاهز للإنتاج.**

# 29. دورات العمل التشغيلية التفصيلية

## 29.1 دورة تهيئة عميل جديد (Tenant Onboarding)

1. إنشاء سجل Tenant بحالة Pending.
2. إنشاء مالك الحساب وربط عضويته.
3. اختيار الخطة أو فترة التجربة.
4. إنشاء Group افتراضية أو ربط العميل بمجموعة قائمة.
5. إنشاء Legal Entity واحدة على الأقل مع بياناتها القانونية والضريبية.
6. إنشاء فرع ومخزن افتراضي ونقطة بيع عند الحاجة.
7. إعداد العملة والمنطقة الزمنية والتقويم والسياسات.
8. إعداد الضرائب والفوترة الإلكترونية بعد استكمال بيانات الشركة.
9. دعوة المستخدمين وتحديد أدوارهم ونطاقاتهم.
10. استيراد الكتالوج والأرصدة الافتتاحية عند الحاجة.
11. فحص جاهزية الإعدادات قبل السماح بالبيع.
12. تحويل Tenant إلى Active بعد استيفاء المتطلبات.

**ضوابط:** لا تنشأ مستندات ضريبية أو أرقام تشغيلية نهائية أثناء معالج الإعداد التجريبي. يجب أن تكون خطوات التهيئة قابلة للاستئناف، مع تسجيل من أكمل كل خطوة. لا تسمح بتفعيل POS إذا كانت الإعدادات الحرجة ناقصة.

## 29.2 دورة البيع في المطعم

1. الكاشير يحدد نوع الطلب: داخل المطعم أو سفري أو توصيل.
2. يحدد الطاولة أو العميل أو قناة الطلب حسب النوع.
3. يضيف الأصناف والمعدلات والإضافات والملاحظات.
4. يتحقق الخادم من صلاحية الأسعار والعروض وتوفر الأصناف.
5. يحفظ الطلب ويرسل تذاكر التحضير إلى محطات المطبخ.
6. تسجل تغييرات حالة التحضير مع المستخدم والوقت.
7. عند طلب الدفع، يحسب الخادم الإجماليات والضريبة والخصم والرصيد.
8. ينفذ الدفع أو يسجل حالة الدفع غير المكتملة.
9. يصدر مستند الفوترة وفق متطلبات ZATCA.
10. يحدث الطلب إلى الحالة المناسبة، ويحرر الطاولة عند اكتمال الخدمة وفق السياسة.
11. يتم استهلاك المخزون وفق توقيت معتمد: عند اعتماد الطلب أو إتمام البيع أو آلية حجز/صرف مرحلية. **قرار مطلوب لكل نموذج تشغيل**؛ يجب ألا يخصم المخزون مرتين.
12. تحفظ روابط الطلب والفاتورة والدفع وتذكرة المطبخ وحركات المخزون.

## 29.3 دورة البيع في الكافيه

تتبع نفس محرك الطلبات، مع واجهة سريعة للمقاسات ودرجة الحرارة ونوع الحليب والسكر والشوتات والنكهات. يجب تمثيل الإضافات كخيارات ذات أسعار وتأثير وصفة واضح، لا كنصوص حرة فقط. يرسل كل مكون إلى محطة التحضير المناسبة.

## 29.4 دورة البيع في التموينات

1. مسح الباركود أو إدخال PLU/رمز صنف موزون.
2. جلب الصنف والوحدة والسعر والضريبة والعرض الفعال.
3. التحقق من الكمية المتاحة والدفعة/الصلاحية عند تطبيقها.
4. إضافة الصنف للسلة.
5. تطبيق قواعد العروض وحدود الكمية.
6. تأكيد الدفع.
7. إصدار الفاتورة.
8. إنشاء حركة صرف المخزون وأثر المحاسبة وفق سياسة الإقفال.

يجب دعم الوزن والكسور ووحدات البيع بدقة، وعدم تقريب الكمية بطريقة تغير قيمة الفاتورة أو تكلفة المخزون.

## 29.5 دورة الوردية

1. تسجيل دخول الكاشير إلى جهاز مصرح به.
2. فتح وردية مرتبطة بالفرع والخزنة والجهاز والمستخدم.
3. تسجيل رصيد افتتاحي نقدي أو تأكيد عدم وجوده.
4. تنفيذ المبيعات والمقبوضات والمصروفات المصرح بها.
5. تسجيل التغذية النقدية والسحب والتحويلات كحركات منفصلة.
6. طلب الإقفال.
7. جلب النظام إجماليات النقد والبطاقات والوسائل الأخرى والمرتجعات والمصروفات.
8. إدخال العد الفعلي للنقد.
9. احتساب الفروق آليًا.
10. اعتماد الإقفال وفق حدود الصلاحية.
11. إنشاء قيد الإقفال المجمع مرة واحدة.
12. إنشاء حركات تسوية الخزينة وحسابات الدفع.
13. قفل الوردية ومنع التعديل المباشر.
14. معالجة أي تصحيح لاحق بقيد/مستند تسوية مرتبط بالوردية الأصلية.

لا يسمح بإقفال وردية لها عملية دفع أو مستند في حالة Unknown دون قرار مصالحة واضح. يمكن إقفالها تشغيليًا مع إبقاء بند التسوية معلقًا فقط إذا سمحت السياسة المحاسبية المعتمدة.

## 29.6 دورة المشتريات

1. إنشاء طلب شراء مع سبب واحتياج.
2. التحقق من الميزانية وحدود الاعتماد.
3. الموافقة أو الرفض مع السبب.
4. إصدار أمر شراء للمورد.
5. تسجيل تأكيد المورد أو التعديل المعتمد.
6. استلام كامل أو جزئي.
7. فحص الكميات والجودة والدفعات والصلاحية.
8. إنشاء حركة مخزون للكمية المقبولة فقط.
9. تسجيل النقص أو الرفض أو التلف.
10. مطابقة فاتورة المورد مع أمر الشراء والاستلام.
11. إنشاء الالتزام والضريبة حسب المستند.
12. توزيع Landed Costs عند انطباقها.
13. سداد المورد بسند دفع مرتبط بالالتزام.
14. معالجة المرتجع أو الإشعار الدائن دون محو الأصل.

## 29.7 دورة التحويل بين المخازن والفروع

- طلب تحويل من جهة مستلمة.
- اعتماد حسب سياسة القيمة/الكمية.
- حجز الكمية من المالك الصحيح.
- إصدار مستند خروج من المصدر.
- تسجيل حالة In Transit.
- استلام جزئي أو كامل في الوجهة.
- تسجيل الفروقات والتلف.
- إقفال التحويل بعد التسوية.
- لا تتغير ملكية المخزون لمجرد انتقاله ماديًا إذا كان التحويل بين مواقع لنفس المالك.
- التحويل بين شركتين قانونيتين يحتاج مستندات وآثارًا محاسبية وضريبية مناسبة، ولا يعامل تلقائيًا كتحويل داخلي.

## 29.8 دورة الجرد

1. إنشاء جلسة جرد بنطاق محدد.
2. تحديد الأصناف والمواقع والدفعات.
3. تحديد ما إذا كان الجرد مع إيقاف الحركة أو مع Cutoff ومتابعة الحركات.
4. تسجيل العد الفعلي مع هوية العادّ.
5. منع رؤية الرصيد النظري في Blind Count إذا اعتمدت السياسة ذلك.
6. إعادة العد للفروقات فوق الحدود.
7. اعتماد الفروقات من شخص مخول.
8. إنشاء حركات تسوية مخزون.
9. إنشاء الأثر المحاسبي.
10. حفظ تقرير الفروقات والأسباب.

## 29.9 دورة الهالك والتالف

- اختيار الصنف والكمية والدفعة والموقع.
- اختيار سبب محدد.
- إرفاق صورة/مستند عند الحاجة.
- اعتماد حسب حدود القيمة.
- إنشاء حركة إخراج.
- تسجيل أثر التكلفة والمصروف.
- تحليل الهالك حسب الفرع والصنف والسبب والمستخدم والفترة.

## 29.10 دورة الإنتاج

1. تحديد وصفة وإصدار فعال.
2. إنشاء أمر إنتاج والكمية المستهدفة.
3. التحقق من توافر المكونات وملكيتها.
4. حجز أو صرف المكونات.
5. تسجيل الاستهلاك الفعلي والفقد.
6. تسجيل الناتج الفعلي والدفعات والصلاحية.
7. احتساب تكلفة الناتج.
8. إنشاء حركة إخراج مواد وحركة إدخال ناتج.
9. إنشاء القيد المحاسبي المناسب.
10. إغلاق الأمر ومقارنة المخطط بالفعلي.

## 29.11 دورة المرتجع

- يجب تحديد نوع المرتجع: قبل/بعد التسليم، كامل/جزئي، قابل لإعادة البيع/تالف.
- ربط المرتجع بالفاتورة الأصلية وبنودها.
- التحقق من الكمية المرتجعة المتبقية وعدم تجاوز الكمية المباعة.
- اعتماد حسب الصلاحية.
- إصدار إشعار دائن/مستند مناسب حسب الحالة ومتطلبات ZATCA.
- إنشاء حركة مخزون فقط إذا عادت البضاعة فعليًا وبحالة قابلة للتخزين.
- إعادة تكلفة المخزون وفق سياسة التقييم.
- عكس/تسوية الإيراد والضريبة والمدفوعات والعمولة عند انطباقها.
- لا يسمح بمرتجع بلا مرجع إلا بصلاحية واستثناء موثق.

## 30.4 ضوابط

- قرار الموافقة يسجل كحدث غير قابل للمحو.
- أي تعديل جوهري بعد الموافقة يعيد الطلب لمسار الموافقة.
- لا تعتمد الواجهة وحدها على إظهار زر الموافقة؛ الخادم يتحقق من السياسة الحالية.
- لا تسمح بتجاوز التسلسل إلا بصلاحية استثنائية مسجلة.
- محرك الموافقات لا يغير الأثر المالي بنفسه؛ بعد الاعتماد تنفذ الوحدة المالكة العملية.

# 31. نموذج الصلاحيات التفصيلي

تستخدم الصلاحيات نمط Resource + Action + Scope.

أمثلة:
- `sales.invoice.create`
- `sales.invoice.discount.approve`
- `sales.return.create`
- `sales.return.approve`
- `inventory.adjustment.create`
- `inventory.adjustment.approve`
- `procurement.purchase_order.approve`
- `accounting.journal.post`
- `accounting.period.close`
- `cashbox.shift.close`
- `platform.tenant.suspend`

كل صلاحية تحدد:
- هل هي على مستوى Tenant أو Group أو Company أو Branch أو Warehouse أو Device؟
- هل تتطلب MFA؟
- هل تتطلب موافقة ثانية؟
- هل لها حد مبلغ/كمية؟
- هل تسمح بالتصدير؟
- هل تسمح برؤية بيانات حساسة؟
- هل تسجل في Audit Log؟

يجب اختبار منع الوصول الأفقي بين الشركات والفروع، ومنع رفع الصلاحيات، ومنع الوصول باستخدام معرفات سجلات متوقعة أو معدلة.

# 32. مصفوفة الأثر المحاسبي والمخزني المرجعية

> هذه المصفوفة توضح المنطق المتوقع على مستوى المفهوم، وليست دليل حسابات نهائيًا أو قيدًا قانونيًا جاهزًا. الحسابات والضرائب النهائية تعتمد على إعدادات الشركة ومراجعة محاسب مختص والمتطلبات المحلية.

| العملية | أثر المخزون | الأثر المحاسبي المفاهيمي |
|---|---|---|
| بيع نقدي | صرف/استهلاك | مدين نقدية، دائن إيراد وضريبة؛ مدين تكلفة مبيعات، دائن مخزون |
| بيع بطاقة | صرف/استهلاك | مدين تسوية بطاقات، دائن إيراد وضريبة؛ قيد تكلفة ومخزون |
| بيع آجل | صرف/استهلاك | مدين عميل، دائن إيراد وضريبة؛ قيد تكلفة ومخزون |
| خصم على البيع | لا أثر مستقل غالبًا | تخفيض الإيراد أو حساب خصومات وفق السياسة |
| مرتجع قابل لإعادة البيع | زيادة مخزون بعد الفحص | عكس/تسوية الإيراد والضريبة والذمم/المدفوعات، وعكس التكلفة |
| مرتجع تالف | لا يعود للمخزون القابل للبيع أو يذهب لحالة حجر | تسوية الإيراد/الضريبة مع إثبات تلف/خسارة حسب الحالة |
| استلام مشتريات غير مفوترة | زيادة مخزون | مدين مخزون، دائن GRNI |
| فاتورة مورد بعد الاستلام | لا حركة كمية جديدة | تسوية GRNI والضريبة والدائنين |
| شراء مباشر مع فاتورة | زيادة مخزون أو مصروف | مدين مخزون/مصروف وضريبة مدخلات، دائن مورد |
| سداد مورد | لا أثر مخزون | مدين مورد، دائن بنك/صندوق |
| مصروف نقدي فوري | لا أثر مخزون غالبًا | مدين مصروف وضريبة مدخلات المؤهلة، دائن صندوق |
| تحويل مخزون بين موقعين لنفس المالك | خروج/دخول بالموقع، دون تغيير إجمالي الملكية | غالبًا لا أثر ربح/خسارة؛ حسب طريقة التسجيل |
| تحويل بين شركتين | خروج من مالك ودخول لمالك آخر | مستندات بيع/شراء أو معالجة Intercompany حسب الحالة القانونية |
| هالك | نقص مخزون | مدين مصروف هالك/خسارة، دائن مخزون |
| زيادة جرد | زيادة مخزون | مدين مخزون، دائن فروق جرد/حساب مناسب |
| عجز جرد | نقص مخزون | مدين فروق جرد/عجز، دائن مخزون |
| إنتاج | تحويل مواد إلى ناتج | نقل تكلفة المواد/تكاليف الإنتاج إلى مخزون الناتج |
| تحصيل عميل | لا أثر مخزون | مدين بنك/صندوق، دائن عميل |
| رسوم مزود دفع | لا أثر مخزون | مدين مصروف رسوم، دائن تسوية مزود الدفع/بنك |
| إقفال وردية | لا حركة كمية جديدة إذا سبق تسجيل الصرف | قيد مجمع للإيراد والضريبة ووسائل الدفع والتكلفة وفق مصدر البيانات |

## 32.1 قواعد منع الازدواج

- يجب تحديد نقطة واحدة فقط لإنشاء حركة صرف المخزون لكل بيع.
- يجب تحديد نقطة واحدة فقط لإنشاء قيد تكلفة المبيعات.
- لا ينشئ كل من POS وإقفال الوردية القيد نفسه.
- يجب أن تحمل كل حركة مصدرًا فريدًا يمنع تكرارها.
- يجب مطابقة إجمالي الفواتير مع إجمالي قيد الإقفال ومصادره.
- يجب فصل تسجيل العملية الضريبية عن توقيت ترحيل القيد المحاسبي.
- لا يجوز أن يؤدي Retry إلى حركة مخزون أو قيد إضافي.

# 33. عقود API — المعايير العامة

## 33.1 القواعد

- كل API يمر عبر طبقة الخادم.
- إصدار API واضح مثل `/api/v1`.
- مصادقة وتفويض قبل تنفيذ Use Case.
- Validation على الخادم.
- لا تثق في tenant_id أو company_id أو branch_id المرسل من العميل؛ استخرجها أو تحقق منها من سياق العضوية.
- استخدم Pagination وFiltering وSorting بقوائم مسموحة.
- استخدم Idempotency للعمليات التي تنشئ أثرًا أو تحصيلًا أو ترحيلًا.
- أعد Correlation ID في الاستجابة.
- لا تعرض Stack Trace أو تفاصيل DB للمستخدم.
- وثق الأخطاء ورموزها.

## 33.2 شكل الاستجابة

استجابة النجاح القياسية تتضمن:
- `data`: النتيجة.
- `meta`: معلومات Pagination أو إصدار المورد عند الحاجة.
- `request_id`: معرف تتبع.

استجابة الخطأ تتضمن:
- `error.code`: رمز ثابت.
- `error.message`: رسالة آمنة ومفهومة.
- `error.details`: تفاصيل تحقق غير حساسة.
- `request_id`: معرف تتبع.

هذه أشكال تعاقدية مفاهيمية؛ يثبت مخطط OpenAPI النهائي لاحقًا.

# 36. إدارة الأجهزة والفروع

## 36.1 سجل الجهاز
لكل جهاز:
- Device UUID.
- Tenant / Company / Branch.
- Device Type.
- اسم الجهاز.
- حالة التسجيل.
- آخر اتصال.
- إصدار التطبيق.
- إصدار Branch Runtime.
- صلاحياته.
- EGS binding عند انطباقه.
- مفاتيح الجهاز/الشهادات عبر مخزن آمن.
- سجل التحديثات والحوادث.

## 36.2 دورة تسجيل الجهاز
طلب تسجيل → تحقق إداري → إصدار اعتماد محدود → تنزيل إعدادات الفرع → فحص الاتصال والطابعة والأجهزة → اختبار بيع تجريبي غير مالي → تفعيل.

إلغاء الجهاز يجب أن يبطل اعتماده ويمنع المزامنة/الطلبات الجديدة، مع حفظ العمليات المحلية غير المزامنة في مسار استعادة آمن قبل المسح.

## 36.3 الأجهزة الطرفية
- الطابعات: تعريف، حالة، قالب، اختبار، إعادة محاولة.
- درج النقدية: فتح فقط بعد حدث دفع/إذن مناسب.
- قارئ الباركود: إدخال آمن ودعم الرموز.
- الميزان: بروتوكول/واجهة موثقة ومعايرة.
- جهاز الدفع: حالة الطلب والتأكيد والرفض والمهلة وUnknown.
- KDS: محطة ومجموعة أصناف وترتيب وأوقات تحضير.

## 36.4 إدارة Branch Server
- تسجيل وربط آمن بالفرع.
- مزامنة إعدادات وسياسات موقعة.
- تحديثات متدرجة مع Rollback.
- Health Monitoring.
- تشفير التخزين المحلي.
- مزامنة وقت آمنة.
- إدارة مساحة التخزين.
- نسخ احتياطي محلي مشفر.
- سجل أحداث محلي.
- لا يحتوي على أسرار سحابية عامة أو مفاتيح لا يحتاجها.

# 37. التقارير ومقاييس الأداء وتعريف المعادلات

يجب تعريف كل KPI بمصدره وفترته واستبعاءاته ومعادلة حسابه.

| المؤشر | التعريف المقترح | ملاحظات |
|---|---|---|
| إجمالي المبيعات قبل الضريبة | مجموع صافي بنود البيع قبل VAT حسب سياسة العرض | يوضح هل يشمل المرتجعات |

يجب ألا تجمع التقارير بيانات شركات بعملات مختلفة دون تحويل موثق وسعر صرف وتاريخ. يجب إظهار مصدر المؤشر وتاريخ آخر تحديث ومستوى دقته.

# 40. معايير القبول التفصيلية حسب الوحدة

## SaaS / Tenant
- لا يمكن لمستخدم Tenant A قراءة أو تعديل بيانات Tenant B بأي endpoint أو تقرير أو ملف.
- تعليق الاشتراك يطبق Entitlements وفق سياسة معلنة ولا يحذف بيانات العميل.
- نقل Dedicated يحافظ على UUID والروابط ويطابق الأرصدة.

## POS / Sales
- الطلب المتكرر بنفس Idempotency Key لا ينشئ فاتورتين.
- لا يطبق سعر قديم إذا انتهت صلاحيته قبل تأكيد البيع.
- لا يتجاوز الخصم صلاحية المستخدم.
- لا تعتبر البطاقة مدفوعة دون تأكيد.
- المرتجع لا يتجاوز الكمية القابلة للإرجاع.
- كل فاتورة مرتبطة بالوردية والطلب والدفع والمستند الضريبي.

## Inventory
- لا يتجاوز الصرف المتاح حسب السياسة.
- لا يمكن تكرار حركة المصدر.
- التحويل لا يخلق أو يفقد كمية دون حركة موثقة.
- الجرد لا يرحل دون اعتماد مطلوب.
- تقييم التكلفة يعاد إنتاجه من الحركات وسجلات التقييم.

## Accounting
- مجموع المدين يساوي مجموع الدائن لكل قيد مرحّل.
- لا يرحل قيد إلى فترة مغلقة دون صلاحية واستثناء.
- لا يتكرر قيد المصدر.
- لا يعدل قيد مرحّل؛ التصحيح بقيد عكسي.
- يمكن تتبع رصيد الحساب إلى القيود المصدرية.

## Procurement
- لا تستلم كمية تتجاوز أمر الشراء إلا بصلاحية وسياسة.
- الاستلام الجزئي يبقي المتبقي مفتوحًا.
- مطابقة الفاتورة تمنع التكرار.
- سداد المورد يقلل الالتزام ولا يكرر المصروف.

## ZATCA
- لا تعرض الفاتورة الكاملة Cleared قبل رد مقبول.
- لا ترسل مستندًا مكررًا بسبب Retry.
- تحتفظ XML والهاش والردود والمراجع.
- حالات الرفض والمصالحة واضحة وقابلة للتتبع.

## Offline
- كل عملية محلية لها معرف ثابت.
- إعادة المزامنة لا تكرر الأثر.
- التعارض المالي/المخزني لا يحل بـLast Write Wins.
- العمليات Unknown لا تعرض كمدفوعة/مقبولة.
- الاستعادة لا تفقد Outbox أو المستندات المحلية.

## Integrations
- Webhook مكرر لا يكرر أثر الأعمال.
- توقيع غير صحيح يرفض.
- فشل المزود يظهر بحالة واضحة.
- الأسرار لا تظهر في Logs أو واجهة العميل.
- Retry له حد وسياسة وDead Letter.

# 41. متطلبات غير وظيفية إضافية

- قابلية الوصول: تباين وأحجام لمس مناسبة للكاشير، وتنقل واضح بالكيبورد حيث يلزم.
- التدويل: لغة واتجاه وعملة وتوقيت وأرقام وتنسيقات محلية.
- قابلية الصيانة: حدود وحدات واضحة، توثيق، اختبارات، وعدم وجود ملفات ضخمة تجمع مسؤوليات متعددة.
- قابلية المراقبة: Correlation ID من الواجهة إلى الخادم والحدث والتكامل.
- قابلية النقل: عدم ربط منطق الأعمال بمزود استضافة واحد دون طبقة تجريد معقولة.
- قابلية التوسع: قياس عنق الزجاجة قبل تقسيم الخدمات.
- الاحتفاظ: سياسات مختلفة للفواتير والسجلات والمحادثات والـLogs والملفات.
- الخصوصية: تقليل البيانات الشخصية وتحديد الغرض والاحتفاظ والوصول.
- التوافق: مصفوفة أجهزة وأنظمة تشغيل وطابعات معتمدة يتم اختبارها فعليًا.

# 43. قائمة POC الإلزامية قبل اعتماد التصميم التنفيذي

1. PWA مقابل Electron: Offline، الطباعة، الأجهزة، التحديثات، التخزين المحلي، الأمان.
2. Branch Server: تثبيت وتحديث واستعادة ومزامنة عدة أجهزة.
3. مخزون Offline: حصص الأجهزة ومنع تجاوز الكمية.
4. الطباعة: 58/80mm وA4، RTL، انقطاع الطابعة وإعادة الطباعة.
5. Payment Terminal: نجاح/رفض/Timeout/Unknown/استعلام حالة/Refund.
6. ZATCA EGS: نموذج الربط والشهادات والمفاتيح والتوقيع والتسلسل وReporting/Clearance حسب أحدث المتطلبات.
7. Shared vs Dedicated: عزل ونسخ احتياطي وتكلفة نقل.
8. PostgreSQL: اختبارات تزامن وترقيم وأحمال ممثلة.
9. WhatsApp Business: قوالب وموافقة العميل وحالات التسليم والتكلفة.
10. Backup/Restore: استعادة كاملة والتحقق من الاتساق.

لكل POC تقرير: الهدف، البيئة، الأجهزة، خطوات الاختبار، النتائج، القياسات، العيوب، القرار والتوقيع.

# 44. قرارات تحتاج المالك — لا تفترضها أداة التنفيذ

هذه قرارات تجارية/تشغيلية يجب أن يختارها مالك المنتج قبل تنفيذ الأجزاء ذات الصلة:

1. هل تكون العملة في واجهة الإصدار الأول SAR فقط مع تجهيز قاعدة البيانات لتعدد العملات، أم تفعيل تعدد العملات من أول إصدار؟
2. هل اعتماد تقييم المخزون يكون لكل شركة أم لكل مخزن؟ التوصية: لكل شركة أولًا.
3. عند تعطل Branch Server: هل يعتمد الاستمرار بحصص مخزون حصرية لكل جهاز؟ التوصية: نعم.
4. هل تكلفة الإنتاج في P0 مواد فقط مع تصميم قابل للتوسع، أم تدخل العمالة والتكاليف غير المباشرة من البداية؟
5. ما نموذج ربط EGS بعد مراجعة متطلبات ZATCA ونتائج POC؟
6. ما مستويات RPO/RTO التي ستقدمها كل باقة؟
7. ما حدود الخطط وأسعارها وسياسة تجاوز الاستخدام؟
8. ما سياسة الاحتفاظ للمحادثات والملفات والـLogs؟
9. هل تفعيل QR Menu والولاء ضمن P0 أم P1؟
10. ما سياسة إلغاء الطلب بعد إرساله للمطبخ أو بدء التحضير؟

لا توقف الدراسة بسبب هذه البنود؛ سجلها كقرارات مفتوحة واطلبها عند الوصول إلى بوابة اعتمادها.

تعتبر المواصفات جاهزة للمراجعة التنفيذية عندما تكتمل المخرجات التالية داخل هذه الوثيقة أو كملاحق داخل نفس الملف:
- SRS مفصل لكل وحدة.
- User Stories وحالات استخدام.
- Workflow لكل دورة عمل.

- API Contract / OpenAPI تفصيلي.

- ERD تفصيلي وData Dictionary.
- Accounting Posting Matrix.
- Inventory Costing Rules.
- ZATCA Compliance Matrix حديثة.
- Offline State Machine وConflict Matrix.
- Integration Connector Contracts.
- Test Cases وAcceptance Criteria.

- خطة ترحيل بيانات وPilot.

**ملاحظة حالة:** النسخة الحالية توسع المواصفات الوظيفية والتقنية، لكنها لا تحتوي بعد على OpenAPI مولد ومراجع، أو ERD رسومي/DDL نهائي، أو مصفوفة ZATCA موثقة بمراجع إصدار حديث، أو نتائج POC. هذه عناصر تحقق ومخرجات تصميم تفصيلية تظل مطلوبة قبل التنفيذ.

# 46. قواعد التسمية والأنواع القياسية للبيانات

## 46.1 أنواع البيانات

| الاستخدام | النوع المنطقي | القاعدة |
|---|---|---|
| معرف داخلي | UUID | غير قابل للتغيير |
| Tenant/Company/Branch ID | UUID | يستخرج من سياق موثوق أو يتحقق منه الخادم |
| مبلغ مالي | DECIMAL/NUMERIC | دقة العملة معلنة؛ لا Float |
| كمية مخزون | DECIMAL/NUMERIC | دقة حسب وحدة القياس |
| سعر صرف | DECIMAL/NUMERIC | دقة أعلى من مبلغ العملة |
| تاريخ ووقت | Timestamp with timezone | يخزن بتوقيت موحد ويعرض حسب Time Zone |
| تاريخ محاسبي | Date | لا يستنتج من وقت الجهاز |
| رمز عملة | CHAR(3) | ISO 4217 |
| رمز دولة | CHAR(2) | ISO 3166-1 alpha-2 |
| حالة | Enum أو جدول مرجعي | انتقالات محددة ومراجعة |
| بيانات مرنة | JSONB | لا تستخدم بدل الحقول الأساسية أو FK |
| رقم مستند | VARCHAR | قيمة عرض منفصلة عن UUID |
| Hash | BYTEA/نص Hex | خوارزمية وطول موثقان |

## 46.2 حقول تدقيق قياسية

تضاف حسب طبيعة الكيان:
- `id`
- `tenant_id`
- `legal_entity_id`
- `branch_id`
- `created_at`
- `created_by`
- `updated_at`
- `updated_by`
- `version`
- `source_system`
- `correlation_id`

لا تضاف كل الحقول آليًا لكل جدول؛ يجب تحديدها حسب الملكية والسياق. الجداول المالية المرحّلة تحتاج أيضًا مرجع المستند المصدر وحالة الترحيل وتاريخ الترحيل ومن قام به.

## 46.3 حقول الحذف والأرشفة

- لا يستخدم `deleted_at` لإخفاء مستند مالي أو ضريبي مرحّل.
- البيانات المرجعية غير المستخدمة يمكن تعطيلها بـ`is_active` أو تاريخ انتهاء.
- حذف المستخدم لا يمحو هوية منشئ العمليات السابقة؛ يستخدم تعطيل الحساب مع الاحتفاظ بمراجع التدقيق وفق سياسة الاحتفاظ.
- المرفقات تحفظ بمرجع آمن وليس بمسار عام قابل للتخمين.

# 49. State Machines — الحالات وانتقالاتها

## 49.1 الطلب

Draft → Submitted → Confirmed → InPreparation → Ready → Served/Dispatched → Completed.

الانتقالات الجانبية:
- Draft → Cancelled.
- Submitted/Confirmed → Cancelled وفق صلاحية وسبب.
- InPreparation → Cancelled فقط وفق سياسة المطبخ مع تسجيل هدر/إلغاء.
- Completed → لا يعاد فتحه؛ التصحيح بمرتجع أو مستند تعديل.

## 49.2 الدفع

Initiated → Authorized → Captured.
مسارات أخرى:
- Initiated → Failed.
- Initiated → Unknown عند انتهاء المهلة دون نتيجة مؤكدة.
- Unknown → Captured أو Failed بعد استعلام موثوق/مصالحة.
- Captured → PartiallyRefunded / Refunded.

لا تنتقل Unknown إلى Captured بمجرد إعادة إرسال طلب الدفع دون تحقق.

## 49.3 المستند المحاسبي

Draft → Validated → Posted → Reversed.

- لا رجوع من Posted إلى Draft.
- Reversed لا يعني حذف الأصل.
- القيد العكسي مرجع مستقل مرتبط بالأصل.
- القيد المرحّل لا يتغير.

## 49.4 الوردية

Open → ClosingRequested → ReconciliationPending (عند وجود حالات معلقة) → Closed.

قد تسمح السياسة بإقفال تشغيلي مع بنود تسوية معلقة، لكن لا يجوز إظهار المطابقة النهائية إذا لم تتحقق.

## 49.5 حركة المخزون

Draft → Validated → Posted → Reversed.

لا يتم تعديل حركة Posted. تصحيحها بحركة عكسية أو تسوية.

## 49.6 الفاتورة الإلكترونية

Draft → Generated → Signed → PendingReporting/PendingClearance → Reported/Cleared.
مسارات:
- Rejected.
- Unknown.
- ReconciliationRequired.

لا تخلط حالة طباعة الإيصال مع حالة الفوترة الإلكترونية.

# 50. تفاصيل عقود API المرجعية

العقود التالية أمثلة دلالية تحدد السلوك المطلوب؛ يجب تحويلها إلى OpenAPI كامل قبل التنفيذ.

## 50.1 إنشاء طلب

`POST /api/v1/orders`

Headers:
- Authorization.
- Idempotency-Key.
- X-Correlation-ID.

Request fields:
- `branch_id` (يُتحقق منه ضمن العضوية).
- `order_type`.
- `channel`.
- `table_id` optional.
- `customer_id` optional.
- `lines[]`: variant_id, quantity, unit_id, modifiers[], notes.
- `requested_price_list_id` optional، ولا يثق الخادم به دون تحقق.

الخادم:
1. يتحقق من المستخدم والنطاق.
2. يتحقق من حالة الفرع والجهاز.
3. يجلب السعر والضريبة الفعالين من مصدرهما.
4. يتحقق من الصنف والوصفة والتوفر.
5. يحسب الإجماليات.
6. ينشئ الطلب وبنوده ذريًا.
7. يكتب Domain Event إلى Outbox.
8. يعيد Order ID وحالته والإجماليات المحسوبة.

أخطاء متوقعة: BRANCH_ACCESS_DENIED، PRODUCT_INACTIVE، PRICE_NOT_AVAILABLE، INSUFFICIENT_STOCK، IDEMPOTENCY_CONFLICT، VALIDATION_FAILED.

## 50.2 تأكيد الطلب

`POST /api/v1/orders/{orderId}/confirm`

- يتطلب Idempotency-Key.
- يعيد التحقق من حالة الطلب والأسعار والتوفر.
- يطبق سياسة الحجز/الصرف.
- ينشئ تذاكر التحضير حسب المحطات.
- يثبت الانتقال إلى Confirmed.
- لا يصدر فاتورة نهائية تلقائيًا إلا إذا كانت سياسة نوع الطلب تنص على ذلك.

## 50.3 تنفيذ الدفع

`POST /api/v1/payments`

Request:
- `order_id`.
- `payment_method`.
- `provider_id` عند الحاجة.
- `amount`.
- `currency_code`.
- `device_transaction_context` عند الحاجة.

السلوك:
- إنشاء محاولة دفع أولًا.
- التواصل مع المزود خارج معاملة DB الطويلة.
- حفظ النتيجة في معاملة منفصلة.
- عند Timeout تحفظ Unknown.
- الاستعلام عن حالة العملية قبل إعادة المحاولة.
- لا ينشأ Capture ثانٍ بسبب Retry.

## 50.4 إقفال الوردية

`POST /api/v1/shifts/{shiftId}/close`

Request:
- `counted_cash`.
- `counted_by_method[]`.
- `variance_reason` عند وجود فرق.
- `closing_notes`.

السلوك:
- قفل تنافسي للوردية.
- التحقق من المستخدم والجهاز.
- حصر كل العمليات ضمن الوردية.
- معالجة/تصنيف العمليات Unknown.
- حساب المتوقع والفروق على الخادم.
- إنشاء قيد الإقفال وحركات التسوية ضمن معاملة ذرية حيث أمكن.
- إنشاء Outbox بعد نجاح الترحيل.
- منع إقفال ثانٍ أو قيد مكرر.

## 50.5 حركة مخزون

`POST /api/v1/inventory/movements`

Request:
- `movement_type`.
- `warehouse_id`.
- `lines[]`: product_variant_id, owner_legal_entity_id, quantity, unit_id, lot_id.
- `source_document_type`, `source_document_id`.
- `reason_code`.

السلوك:
- تحقق من الملكية والصلاحية والوحدة والدفعة.
- تحقق من الرصيد أو الحصة المحلية.
- قفل/تحديث ذري للرصيد عند الحاجة.
- إنشاء الحركة وبنودها.
- تحديث Projection الرصيد.
- إنشاء حدث Outbox.
- لا تسمح بتكرار المصدر.

## 50.6 ترحيل قيد

`POST /api/v1/accounting/journal-entries/{id}/post`

- تحقق من توازن المدين والدائن.
- تحقق من الحسابات والكيان والفترة.
- تحقق من المصدر وعدم ترحيله سابقًا.
- تحقق من صلاحية المستخدم والموافقات.
- خصص رقم القيد ذريًا.
- ثبت Posted ووقت وفاعل الترحيل.
- لا تسمح بتعديل القيد بعد ذلك.
- عند التكرار أعد نتيجة العملية السابقة أو خطأ حالة واضحًا.

## 50.7 اعتماد جرد

`POST /api/v1/inventory/stock-counts/{id}/approve`

- تحقق من اكتمال العد وإعادة العد المطلوبة.
- تحقق من فصل العادّ عن المعتمد عند اشتراط السياسة.
- احسب الفروق على الخادم.
- أنشئ حركات التسوية مرة واحدة.
- أنشئ الأثر المحاسبي.
- اقفل جلسة الجرد.

## 50.8 استقبال Webhook

`POST /api/v1/integrations/webhooks/{connectionId}`

- تحقق من التوقيع والوقت ومصدر الاتصال.
- خزّن معرف الحدث الخارجي وPayload Hash.
- ارفض أو تجاهل المكرر بطريقة آمنة.
- سجل Inbox Event.
- أعد استجابة سريعة بعد قبول الحدث وفق عقد المزود.
- نفذ المعالجة في Worker.
- انقل الفشل النهائي إلى Dead Letter.
- لا تنفذ منطق أعمال ثقيلًا داخل طلب Webhook.

# 57. مواصفات الشاشات الأساسية — الإصدار الأول

> مواصفات تصميم وسلوك قابلة للتحويل إلى مهام تنفيذ. وجود المواصفات لا يعني أن الشاشات بُنيت أو اختُبرت.

## 57.1 قواعد مشتركة

1. إظهار الشركة والفرع والمخزن والجهاز النشط في سياق الشاشة.
2. لا يسمح بتغيير السياق إلى نطاق خارج صلاحية المستخدم.
3. إظهار حالة الاتصال: Online / Branch Server / Offline / Syncing / Sync Error.
4. كل عملية حفظ تميز بين نجاح الخادم والحفظ المحلي غير المتزامن.
5. لا تعرض رسالة نجاح عند حالة Unknown أو Pending.
6. توضيح العملة والضريبة والإجمالي قبل الضريبة وبعدها.
7. رسائل التحقق تشغيلية ومفهومة، مع Correlation ID للأخطاء التقنية.
8. البحث والترشيح والترتيب والصفحات تنفذ من الخادم.
9. العمليات المالية والمخزنية الحساسة تسجل السبب والموافق.
10. المستند المرحّل لا يعدل أو يحذف؛ التصحيح بعكس أو تسوية أو مستند مرتبط.

## 57.3 قواعد POS

- عرض السعر والضريبة والخصم والإجمالي قبل الدفع.
- السعر اليدوي والخصم الاستثنائي يحتاجان صلاحية وسببًا وموافقة حسب الحد.
- تقسيم الدفع مسموح إذا أعدته المنشأة.
- كل محاولة دفع لها Payment Attempt ID مستقل.
- نتيجة دفع Unknown لا تتحول إلى Paid قبل المصالحة.
- تعليق الطلب واستعادته يخضعان لسياسة حجز مخزون وزمن.
- إعادة الطباعة لا تنشئ فاتورة أو دفعة جديدة.
- البيع الصادر لا يحذف؛ يستخدم إلغاء أو مرتجع أو إشعار دائن وفق الحالة.
- عند Offline تظهر العمليات المتاحة والممنوعة بوضوح.

## 59.1 قواعد منع الأخطاء

- تحويل البضاعة بين مخازن أو فروع للكيان القانوني نفسه ليس إيرادًا.
- صرف بضاعة لمشروع داخلي أو مركز تكلفة لا ينشئ إيراد بيع تلقائيًا؛ يعالج كمخزون/استهلاك/تكلفة مشروع.
- البيع بين شركتين قانونيتين مختلفتين يحتاج معالجة Intercompany وضريبية صحيحة.
- تحصيل فاتورة مسجلة لا يعيد تسجيل الإيراد.
- إيداع النقدية بالبنك ليس مبيعات.
- القيد الآلي يحمل `source_type`, `source_id`, `posting_batch_id`, `idempotency_key`, `accounting_period_id`.
- يمنع تكرار الترحيل بقيد فريد ومفتاح idempotency.
- يمنع الترحيل إذا كان القيد غير متوازن أو المصدر غير مكتمل أو الفترة مغلقة.
- القيد المرحّل لا يعدل؛ التصحيح بقيد عكسي مرتبط.

- لا تضع أسرارًا أو بيانات بطاقات أو بيانات شخصية غير لازمة في Payload.
- تسليم الحدث لا يعني اكتمال الأثر الخارجي؛ حالة التكامل منفصلة.

# 62. Threat Model — نموذج التهديدات

| التهديد | الأثر | الضوابط | الكشف والاستجابة |
|---|---|---|---|
| Tenant ID manipulation | تسرب بيانات عميل | اشتقاق النطاق من الهوية، RLS، فحص Server-side | تنبيه ومحاولات اختبار عزل |
| Broken Object Authorization | الوصول لسجل غير مصرح | تحقق لكل Object وEndpoint | اختبارات BOLA |
| Privilege escalation | اعتماد/ترحيل دون صلاحية | Scopes وفصل المهام | Audit وتنبيه تغييرات الأدوار |
| Duplicate payment | تحصيل مزدوج | Idempotency وPayment Attempt ومصالحة | تنبيه ومراجعة |
| Replay webhook | إعادة تنفيذ عملية | توقيع وتوقيت وNonce/Deduplication | رفض الطلب المكرر/القديم |
| Secret leakage | اختراق تكامل أو EGS | Secret Manager وإخفاء Logs وتدوير | Secret scanning واستجابة |
| Private key theft | تزوير أو تعريض الفوترة | تخزين محمي وأقل صلاحية وإدارة مفاتيح | إبطال/تدوير وفق الإجراء |
| Injection/XSS/CSRF | تنفيذ أوامر غير مصرح | Parameterization وEncoding وCSP وCSRF controls | SAST/DAST |
| Ransomware أو حذف إداري | فقد البيانات | نسخ معزولة وMFA وفصل صلاحيات | Restore drills |
| سرقة جهاز Offline | كشف بيانات محلية | تشفير وقفل وصلاحية محدودة | إبطال عند الاتصال |
| Supply-chain attack | إدخال كود خبيث | Lockfiles وSBOM وفحص dependencies | مراقبة CVE |
| DoS/Abuse | توقف أو تكلفة مرتفعة | Rate limits وquotas وWAF وحدود Queue | مراقبة وتنبيه |
| Insider misuse | تسريب/تعديل متعمد | فصل مهام وسجل غير قابل للتلاعب ووصول مؤقت | مراجعات وتنبيهات |
| Data export exfiltration | تسريب تقارير | صلاحية تصدير مستقلة وحدود | Audit للتصدير |
| Clock manipulation | فساد التسلسل والتوقيت | Server time وتسلسل ذري | فحص انحراف الساعة |

بوابات الأمن قبل Pilot: مراجعة Threat Model، اختبار عزل Tenant/Company/Branch، SAST وDependency/Secret scanning، DAST، مراجعة RLS، MFA وإبطال الجلسات، Restore Test، مراجعة دعم النظام، معالجة وإعادة اختبار الثغرات الحرجة، واختبار اختراق مستقل قبل الإطلاق العام.

# 67. الحالة الواقعية للوثيقة

## 67.1 موثق بدرجة تصميم جيدة
الرؤية والنطاق، الهيكل متعدد العملاء والشركات والفروع، الوحدات الأساسية، دورات التشغيل، مبادئ المحاسبة والمخزون، Offline، الأمن، شاشات P0، الصلاحيات الأساسية، اختبارات القبول المرجعية، ومراحل التنفيذ.

## 67.2 ما لا يزال يتطلب مخرجات أو تحققًا حقيقيًا
1. ERD فيزيائي نهائي بكل الأعمدة والأنواع والقيود والفهارس.
2. OpenAPI كامل قابل للتحقق آليًا لكل Endpoint.
3. مراجعة ZATCA حديثة تربط كل حقل وتوقيع وتسلسل بمرجع رسمي وإصدار نافذ.
4. POCs فعلية للطباعة والدفع وEGS وOffline.
5. مراجعة محاسب سعودي ومختص ضريبة وفوترة إلكترونية.
6. Permission Matrix نهائية بعد اعتماد الوظائف الفعلية.
7. الأسعار وحدود الاشتراكات بعد قياس Pilot.
8. RPO/RTO وRestore Test.
9. Load Test وPenetration Test.
10. Pilot حقيقي.

## 67.3 متى نقول إن التصميم مقفول؟
يكون التصميم مقفولًا عندما يعتمد المالك القرارات الستة أو التوصيات الافتراضية، وتراجع المصفوفات المحاسبية والضريبية، ويعتمد ERD وOpenAPI وPermission Matrix التفصيلية، وتغلق تعارضات النطاق والعمليات الحرجة.

أما جاهزية المنتج للإطلاق فلا تتحقق إلا بعد البناء والاختبارات والـPOCs والمراجعات والتشغيل التجريبي. إغلاق الوثيقة لا يعني أن منتجًا لم يُبنَ أصبح جاهزًا للإنتاج.

| 4 | دعم عدة شركات قانونية من البداية داخل المجموعة | Multi-Entity من الأساس؛ Pilot بكيان واحد ثم اختبار مجموعة متعددة الشركات |
| 5 | تأجيل أسعار الاشتراكات حتى قياس تكلفة التشغيل ونتائج Pilot | بناء محرك الباقات والحدود والفوترة دون تثبيت أسعار |
| 6 | اختيار مزود الدفع والطابعة والأجهزة بعد تقييم الوثائق وSDK والتوافر والدعم المحلي | لا تثبيت لمزود أو جهاز قبل تقييم موثق وPOC |

## 69.1 سياسة Offline quota leases المعتمدة

- Branch Server هو المنسق المحلي ما دام متاحًا.
- عند الاتصال به، تخصص حصص مخزون محددة لكل جهاز بحسب الصنف والمخزن والمالك، بتخصيص ذري من خدمة المخزون.
- لا تنشأ الحصة من رصيد واجهة المستخدم، ولا يستطيع الجهاز استخدام حصة جهاز آخر أثناء الانقطاع.
- كل عملية Offline تحمل Device ID وLocal Sequence وIdempotency Key ووقت الجهاز ووقت الاستلام عند المزامنة.
- وقت الجهاز وحده لا يحسم الترتيب المالي أو القانوني؛ يعتمد الخادم التسلسل الموثوق وسجلات EGS.
- إعادة المزامنة لا يجوز أن تكرر البيع أو حركة المخزون.
- عند نفاد الحصة أو انتهائها، يمنع بيع الصنف المخزني أثناء العزل.
- لا يفترض دعم الدفع الإلكتروني أو البيع الآجل Offline؛ يسمح به فقط إذا أثبت المزود دعمه صراحة وبآلية موثوقة.
- عند تعذر ضمان عدم التكرار أو سلامة التوقيع والتسلسل، تتوقف الوظيفة المتأثرة ويظهر سبب المنع.
- يجب اختبار تعطل السيرفر، نفاد الحصة، انتهاء صلاحيتها، إعادة تشغيل الجهاز، عدة أجهزة، وتعارض المزامنة.

## 69.2 حدود الاعتماد

اعتماد المالك يغلق القرارات التجارية الستة على مستوى التصميم فقط. لا يمثل موافقة محاسب أو ZATCA أو مزود دفع، ولا يثبت نجاح POC أو اختبار. أي تغيير لاحق يمر عبر Change Request وADR وتقييم أثر.

## 71.10 فهارس وقيود حرجة

1. كل جدول تابع لعميل يحمل tenant_id أو يمكن اشتقاقه بعلاقة إلزامية لا تسمح بعبور Tenant.
2. فهارس مركبة تبدأ غالبًا بـ tenant_id ثم company/branch/status/date وفق نمط الاستعلام الفعلي.
3. Unique constraints على document numbers ضمن الشركة ونوع المستند/نطاق الفرع وسياسة السنة.
4. Unique على idempotency keys في العمليات المالية والـwebhooks والـoutbox consumers.

7. لا يستخدم التطبيق `MAX(number)+1` مطلقًا.
8. جميع قيود Tenant/Company لا تعتمد على UI؛ تتحقق في الخادم وDB/RLS عند توفرها.
9. لا يسمح بحذف السجلات المالية/المخزنية المرحّلة؛ Soft delete للبيانات المرجعية فقط عند الحاجة وبشروط.
10. كل عملية تعديل رصيد أو ترقيم أو ترحيل قيد تتم في Transaction واحدة مع Locks/Constraints مناسبة.

# 72. OpenAPI Contract — المسارات الأساسية المقترحة

> هذه مواصفة عقد API مرجعية، وليست API منشورة. جميع المسارات تحت `/api/v1`. المصادقة عبر OIDC/OAuth2 access token، والنطاق يشتق من الهوية ولا يثق في tenant_id يرسله العميل. كل Endpoint حساس يسجل correlation ID ويعيد Error Envelope موحدًا.

## 72.1 قواعد HTTP العامة

- `POST` للإنشاء/الأوامر، `GET` للقراءة، `PATCH` لتعديل Draft فقط، ولا يوجد تعديل مباشر لمستند Posted.
- `Idempotency-Key` إلزامي للإنشاءات المالية/الطلبات/الدفع/الترحيل/الـwebhooks التي يمكن إعادة إرسالها.
- `If-Match` أو version field مطلوب للتعديلات المتزامنة على Draft/Settings.
- Pagination: `page_size` بحد أعلى، و`cursor` opaque؛ لا offset عميق في الجداول الضخمة.
- الوقت في API بصيغة ISO-8601 UTC؛ العملة ISO 4217؛ المبالغ والكميات ترسل كسلاسل Decimal لتجنب Float.
- الأخطاء بصيغة `{code,message,correlation_id,details,retryable}` دون كشف stack trace أو SQL.

## 72.2 المسارات

### إنشاء طلب بيع

### إنشاء محاولة دفع

`POST /api/v1/sales/orders/{id}/payments`

```json
{
  "payment_method":"card",
  "provider_code":"configured_provider",
  "amount":"23.00",
  "currency":"SAR",
  "terminal_id":"configured-terminal"
}
```

Response: `202` مع `payment_attempt_id` و`status` مثل `initiated` أو `unknown`. لا يصدر نجاح نهائي حتى تأكيد المزود أو المصالحة.

### إقفال وردية

`POST /api/v1/pos/shifts/{id}/close`

```json
{
  "counted_cash":"500.00",
  "tender_totals":[
    {"method":"cash","amount":"500.00","currency":"SAR"},
    {"method":"card","amount":"1200.00","currency":"SAR"}
  ],
  "variance_reason":null,
  "expected_version":7
}
```

Response `202` أو `200` حسب اكتمال المعالجة، مع `shift_status`, `posting_batch_id`, `journal_entry_id` عند الترحيل، أو حالة معلقة صريحة. لا تعرض `closed` إذا لم يثبت إقفالها وترحيلها وفق السياسة.

### استقبال Webhook

`POST /api/v1/integrations/webhooks/{provider}`

- تحقق من التوقيع على raw body قبل parsing وفق عقد المزود.
- تحقق من timestamp/replay window إذا كان المزود يدعم ذلك.
- احفظ Event ID وPayload Hash في Inbox بقيد Unique.
- أعد استجابة الاستلام فقط بعد حفظ الحدث بأمان؛ المعالجة غير المتزامنة مستقلة.
- لا تثق بمبلغ أو حالة دفع من دون تحقق من توقيع/استعلام موثوق لدى المزود.

## 73.1 ما تم التحقق منه من المصادر الرسمية

| الموضوع | المتطلب/المرجع المثبت | أثره على التصميم |

## 73.2 متطلبات EGS داخل المنتج

1. فصل `POS Device` عن `EGS Unit` وعن `Branch Server` وعن `Central Submission Service`.
2. كل EGS Unit تسجل بيانات التعريف المطلوبة، الرقم التسلسلي، الموديل/الإصدار، الموقع، ملف أنواع الفواتير، حالة CSID، تاريخ الانتهاء والإلغاء.
3. تعيين نقطة إصدار الفاتورة إلى EGS Unit محددة وفق إعداد قانوني وتشغيلي موثق؛ لا يسمح بتبديلها عشوائيًا أثناء التسلسل.
4. تخزين مرجع الشهادة والمفتاح الخاص في Secret Store أو HSM/وسيلة محمية مناسبة؛ ممنوع تخزين Private Key في React أو LocalStorage أو جدول مكشوف.
5. إدارة CSID onboarding/renewal/revocation كعمليات مستقلة تتطلب صلاحية وموافقة وسجل تدقيق.
6. ICV وPIH وسلسلة الهاش تخص EGS Unit وفق مواصفات الهيئة؛ التخصيص ذري، ولا يعاد استخدام رقم/تسلسل سبق استهلاكه.
7. XML الموقع وHash وSignature وQR snapshots غير قابلة للتعديل؛ التصحيح بمستند نظامي جديد.
8. حفظ Request/Response/Validation outcome/Warnings/Errors ووقت الإرسال ومراجع الأدلة.
9. عدم اعتبار Sandbox أو SDK نجاحًا في الإنتاج أو اعتمادًا رسميًا للمنتج.
10. عند فقد الجهاز أو سرقة مفتاحه، تفعيل مسار إيقاف/إلغاء CSID وفق الإجراء الرسمي وتوثيق الواقعة.

## 73.3 مسارات المستندات

| نوع المستند | مسار التكامل | الحالة التي تسمح باعتباره مكتملًا |
|---|---|---|
| Tax Invoice / Credit-Debit Note المرتبطة بها | Clearance | استجابة Clearance المطلوبة من FATOORA، مع حفظ الرد والنسخة المعتمدة |
| Simplified Tax Invoice / Credit-Debit Note المرتبطة بها | Reporting | قبول/نتيجة Reporting وفق المتطلبات والمهلة النافذة للمكلف |
| مستند غير متصل مؤقتًا | حفظ محلي آمن وفق القيود الرسمية ثم مزامنة/إرسال | لا يسمى Cleared/Reported قبل استجابة الهيئة؛ وتطبق مهلة ومتطلبات النظام الفعلية |
| مستند مرفوض | لا يعتبر مقبولًا | حالة Rejected مع السبب ومسار تصحيح/إعادة تقديم مسموح دون تغيير مستند موقع بطريقة غير نظامية |

**تنبيه مهم:** لا تثبت هذه الوثيقة مهلة زمنية محددة للتبليغ أو قواعد استثناء Offline. يجب استخراج المهلة الدقيقة من أحدث نص نافذ للقرار والملحقات والتعاميم المنطبقة على نوع المكلف والمستند قبل كتابة منطق Timer أو SLA في الكود. لا تستخدم عبارة عامة مثل «خلال 24 ساعة» دون توثيق رسمي مباشر نافذ.

## 73.4 State Machine المقترحة

`Draft → Validated → Generated → Signed → Queued → Submitted → (Reported | Cleared | Rejected)`.

حالات تشغيلية إضافية: `Submission Unknown`, `Retry Scheduled`, `Reconciliation Required`, `Revoked Credential`, `Expired Credential`. لا ينتقل المستند من `Rejected` إلى `Cleared` بتغيير الحالة فقط؛ ينشأ إجراء تصحيح نظامي موثق وفق سبب الرفض.

# 74. Offline POS — بروتوكول الحصص والمزامنة

## 74.1 نموذج الحصة

لكل حصة مخزون: `lease_id`, `tenant_id`, `legal_entity_owner_id`, `warehouse_id`, `item_id`, `device_id`, `allocated_qty`, `consumed_qty`, `reserved_qty`, `issued_at`, `valid_until`, `server_epoch`, `signature`, `status`.

- الحصة موقعة من Branch Server أو خدمة مخزون موثوقة، ومقيدة بجهاز ومالك ومخزن وصنف.
- لا يمكن تعديل الكمية محليًا أو نقل الحصة بين الأجهزة.
- لا تصدر حصة جديدة إذا كان مجموع الحصص غير المستهلكة يتجاوز المتاح القابل للتخصيص.
- تحرير الحصة غير المستهلكة يتطلب اتصالًا موثوقًا أو انتهاء صلاحيتها وفق آلية تمنع جهازًا معزولًا من مواصلة الاستهلاك بعد انتهاء الحصة.
- الحصة لا تعني أن النظام يضمن مخزونًا عالميًا دقيقًا أثناء انقطاع جميع الاتصالات؛ هي حد أقصى محجوز مسبقًا.

## 74.2 Local transaction envelope

كل عملية محلية تسجل: `device_id`, `device_epoch`, `local_sequence`, `operation_id`, `idempotency_key`, `lease_id`, `payload_hash`, `occurred_at_device`, `created_at_local`, `signature_or_integrity_proof`, `sync_status`.

- التسلسل المحلي monotonic ولا يعاد إلى الصفر عند إعادة تشغيل التطبيق؛ device_epoch يتغير بإجراء تسجيل/تهيئة موثق.
- البيانات المحلية مشفرة، ولا تخزن أسرار الدفع أو مفاتيح EGS في تخزين الواجهة.
- Local DB transaction تحفظ الطلب والحصة والحدث المحلي كوحدة واحدة.
- لا يعرض التطبيق نجاحًا إذا لم يثبت Commit محلي durable وفق POC.

## 74.3 مزامنة الخادم

1. المصادقة على الجهاز والتحقق من حالته ونسخته.
2. التحقق من توقيع/سلامة حزمة المزامنة ومفتاح الحصة.
3. ترتيب العمليات ضمن device_epoch وlocal_sequence.
4. فحص Idempotency Key وPayload Hash.
5. التحقق من استهلاك الحصة وعدم تجاوزها.
6. إعادة التحقق من قواعد السعر والضريبة وحالة الصنف وفق Snapshot/قواعد الإصدار وقت البيع.
7. إنشاء الحركات المركزية مرة واحدة داخل Transaction.
8. رد لكل Operation بنتيجة `accepted`, `duplicate`, `rejected`, `needs_review` مع سبب.
9. عدم إعادة إرسال عمليات مقبولة على أنها جديدة؛ يحتفظ الجهاز بإيصال مزامنة.
10. الحالات المالية أو الضريبية المجهولة تذهب إلى Reconciliation Queue.

| الوظيفة | الإنترنت فقط مفصول وBranch Server يعمل | Branch Server متعطل والجهاز يعمل بحصة | ملاحظة |
|---|---|---|---|

# 76. Definition of Done — شروط تسليم كل وحدة

كل وحدة لا تعتبر منجزة إلا إذا تحققت البنود التالية:

1. Business rules موثقة ومغطاة باختبارات.
2. صلاحيات القراءة والكتابة والاعتماد والتصدير مفصولة ومختبرة.
3. Tenant/Company/Branch scope enforced server-side.
4. Database constraints تمنع الحالة غير الصحيحة حتى عند التزامن.
5. Idempotency على الأوامر القابلة لإعادة الإرسال.
6. Audit trail للعمليات الحساسة مع actor/source/correlation ID.
7. حالات Loading/Empty/Error/Offline/Retry واضحة في الواجهة.
8. Pagination وIndexes وقياس استعلامات الشاشة.
9. Unit + Integration + Acceptance tests ناجحة.
10. API contract وEvent schema موثقان ومراجعان.
11. Migration وRollback وخطة البيانات موثقة.
12. لا توجد ثغرات Critical/High غير معالجة دون قبول مخاطر رسمي.
13. مراقبة وتنبيهات وسجلات تشغيلية متاحة.
14. دليل تشغيل ودعم مختصر للمستخدم/المشغل.
15. مراجعة Product Owner ومراجع المجال (محاسبة/ضريبة/مخزون) عند انطباقه.
